# Neo4j 知识图谱和 Graph RAG

前置文档：[RAG](/articles/rag)

我一开始觉得，知识库有了向量检索，再加上 ElasticSearch 关键词检索，应该就够用了。

向量检索负责找“意思差不多”的内容，关键词检索负责查接口名、错误码、文件路径这些精确信息。

看起来短板已经互补了，但我后来发现，这两种检索都有一个共同问题：**它们擅长找内容，但不擅长查关系。**

比如我们想知道：

- 一个需求由哪个页面实现？
- 这个页面调用了哪些接口？
- 某个接口变更后，会影响哪些模块？
- 这些模块最近被谁修改过？

单纯搜索，可能会返回需求文档、接口文档和代码提交记录。

但它不一定能直接给出：

> 需求 → 页面 → 模块 → 代码变更 → 接口

这条完整的关系链路。

这就是图数据库开始有价值的地方。

## Neo4j 是什么

我们平时用 MySQL、PostgreSQL，主要是把数据放到一张张表里，再通过字段、外键和关联表把它们连起来。

Neo4j 不一样，它直接把数据存成“节点”和“关系”。

比如一个技术知识库里，可以有需求、页面、模块、接口、代码变更和研发人员这些节点。

然后再给它们加上关系：

![业务实体关系示例](/images/neo4j-entity-relationship.png)

这时候查一个需求，就可以顺着关系继续查页面、模块、接口和修改记录。

返回的不再是一堆零散文本，而是一条有明确语义的路径。

Neo4j 用 Cypher 做查询，可以先把它理解成图数据库里的 SQL。

比如查一个需求对应的页面、模块、代码变更和接口：

```cypher
MATCH (requirement:Requirement {id: $requirementId})
      -[:IMPLEMENTED_BY]->(page:Page)
      -[:LOCATED_IN]->(module:Module)
      <-[:CHANGES]-(change:CodeChange)
OPTIONAL MATCH (page)-[:CALLS]->(api:ApiEndpoint)
RETURN requirement, page, module, change, collect(api) AS apis
LIMIT $limit
```

这段查询表达的就是一条业务链路。

说白了，关系型数据库也能查关系，但当关系类型越来越多，还要查可变长度的多跳路径时，图数据库的表达会更直接。

## Graph RAG 是什么

有了知识图谱之后，怎么和大模型串起来？

其实思路很简单：

用户先问一个问题，模型识别问题里的实体和关系，再选择合适的图查询。

图数据库返回节点和关系后，系统把查询结果、来源和证据放进 Prompt，最后再让大模型组织回答。

![Graph RAG 查询流程](/images/graph-rag-query-flow.png)

传统 RAG 检索的主要是文档片段，Graph RAG 检索的主要是实体和关系。

它不是把原来的 RAG 推翻了，而是多了一种检索方式。

## 让模型生成 Cypher，就算 Graph RAG 了吗

有的同学可能会问：

让大模型生成一段 Cypher，然后查一下 Neo4j，这就是完整的 Graph RAG 了么？

这只能算一个最小版本，适合先把查询链路跑通。

真正想把它做完整，还要解决这些问题：

- 怎么从文档里抽取实体和关系
- 怎么合并同一个实体，避免重复节点
- 怎么记录关系来自哪篇文档和哪个版本
- 文档变化之后，怎么增量更新图谱
- 怎么融合向量、关键词和图谱检索结果
- 怎么评估关系抽取和最终回答是否准确

微软的 GraphRAG 还会做图聚类、社区摘要，并且区分本地查询和全局查询。

所以生成 Cypher 只是查询阶段的一种实现，并不是 Graph RAG 的全部。

## 三种检索到底有什么区别

这三种检索不是二选一，而是各干各的活。

### 向量语义检索

适合用户用自然语言提问，但没有明确关键词的场景。

比如用户问“登录失败怎么处理”，文档里写的却是“身份认证异常排查”。

字面不一样，但意思差不多，这种就适合向量检索。

### ElasticSearch 关键词检索

适合接口名、错误码、需求编号、文件路径、类名这些需要精确匹配的内容。

它还擅长字段过滤、时间排序、分词和高亮。

要查明确的专业术语和固定关键词，交给它比较合适。

### Neo4j 知识图谱检索

适合查实体关系、层级结构和多跳链路。

比如查一个需求属于哪个应用，一个页面依赖哪些接口，一个接口变化会影响哪些模块。

要查关系、依赖、上下游和影响范围，交给知识图谱。

三种检索组合起来，流程大概是这样的：

![混合检索与权限过滤流程](/images/hybrid-retrieval-flow.png)

普通的文档问答可以走向量和关键词检索。

当问题涉及依赖、影响范围和上下游关系时，再增加图谱的多跳查询。

最后把结果融合、重排，再做一次权限过滤，才能放进 Prompt。

## 生产环境不能直接执行模型生成的 Cypher

学习示例里，让模型生成 Cypher 然后直接执行，这样做没什么问题。

但生产环境不能这么玩。

模型可能生成删除、修改语句，也可能生成没有范围限制的路径查询，一次拉回非常多数据。

所以至少要做这些限制：

- Neo4j 使用只读账号
- 只允许 `MATCH`、`OPTIONAL MATCH`、`WITH`、`RETURN`
- 节点类型、关系类型、字段和最大跳数使用白名单
- 强制加上权限条件、`LIMIT` 和查询超时
- 执行前先解析或者调用 `EXPLAIN`，发现写操作直接拒绝
- 常用场景尽量使用固定查询模板，模型只选模板和生成参数

比如用户问“这个需求影响了哪些接口”，模型不需要自由发挥写一整段 Cypher。

系统可以提前准备好“需求影响接口”的查询模板，让模型只负责提取需求编号。

这样稳定很多，也安全很多。

## 图谱里的关系要有证据

还有一个很重要的问题：

图谱里的关系是从哪里来的？

比如“这个需求由这个模块实现”，不能只是模型觉得它们语义相似，就直接写一条边。

每条关系最好都记录来源对象、来源版本、提取方式、置信度和是否经过人工确认。

能通过编号、地址、文件路径明确关联的，优先用确定性规则。

只有没有明确规则的时候，再用大模型抽取，并且保留审核和失效机制。

不然图谱看起来很丰富，但里面的关系是错的，最后多跳推理只会错得更远。

## 现在要不要马上引入 Neo4j

知识图谱很适合查关系，不代表系统现在就一定要加 Neo4j。

很多一跳、两跳查询，用关联表、递归 CTE 和物化视图也能做。

为了 Graph RAG 这个名字就马上增加一套数据库，没有必要。

只有出现这些情况，才值得专门验证 Neo4j：

- 多跳和可变长度路径已经成为高频查询
- 关系类型越来越多，SQL 很难维护
- 影响分析和依赖链路能明显提高回答质量
- 原有数据库的关系查询达不到延迟要求
- 团队能承担图谱同步、权限、备份、监控和评估成本

我更倾向先选一条真实的多跳链路，用原有数据库和 Neo4j 分别查一次。

对比正确率、查询速度、维护成本和结果的可解释性。

Neo4j 真的带来明显收益，再正式引入。

## 总结

向量检索擅长找语义相近的内容，ElasticSearch 擅长找包含关键词的内容，Neo4j 擅长查实体关系和多跳链路。

把问题理解、图查询、结果整理和大模型回答串起来，就是一个最小版本的 Graph RAG。

但真正难的不是“让模型写一段 Cypher”，而是关系抽取、实体合并、增量更新、权限过滤、证据追踪和效果评估。

所以最终要不要引入 Neo4j，不是看这个概念有多火，而是看真实的多跳查询能不能明显提高检索和回答的质量。
